# StockFlow API

**StockFlow** — REST API для управления складскими остатками и движением товаров, разработанный на Django REST Framework и PostgreSQL.

Сервис позволяет вести учёт товаров на нескольких складах, регистрировать поступления и списания, контролировать доступные остатки и просматривать историю операций.

Особое внимание уделено целостности данных, транзакционной обработке складских операций и защите от некорректного списания при параллельных запросах.

## Технологический стек

- **Backend:** Python 3.12, Django 5.2, Django REST Framework
- **База данных:** PostgreSQL 16
- **Контейнеризация:** Docker, Docker Compose
- **Документация API:** OpenAPI, drf-spectacular, Swagger UI
- **Тестирование:** pytest, pytest-django
- **Качество кода:** Ruff
- **CI:** GitHub Actions
- **Application server:** Gunicorn

## Возможности

- Управление справочниками товаров и складов.
- Просмотр складских остатков с фильтрацией.
- Регистрация поступлений и списаний товаров.
- Проверка достаточности остатка перед списанием.
- Запрет операций с неактивными товарами.
- Атомарное обновление остатков и запись операций в журнал.
- Блокировка строк PostgreSQL через `select_for_update()` при изменении остатков.
- Разграничение прав доступа между обычными пользователями и сотрудниками.
- Автоматическая документация REST API.
- Автоматизированные тесты, включая конкурентное списание.

## Архитектура

Проект разделяет HTTP-слой, валидацию данных и бизнес-логику.

| Компонент | Ответственность |
|---|---|
| `inventory/models.py` | Модели товаров, складов, остатков и движений |
| `inventory/serializers.py` | Сериализация и валидация данных API |
| `inventory/views.py` | Обработка HTTP-запросов и контроль доступа |
| `inventory/services.py` | Транзакционная бизнес-логика складских операций |
| `inventory/tests/` | Автоматизированные тесты |
| `config/settings.py` | Конфигурация Django и подключение базы данных |

### Целостность складских операций

Поступления и списания обрабатываются сервисной функцией `apply_movement()`.

Операция выполняется внутри `transaction.atomic()`, благодаря чему изменение остатка и создание записи в журнале происходят в одной транзакции.

При списании существующая строка остатка блокируется с помощью `select_for_update()`. После получения блокировки проверяется доступное количество товара.

Если товара недостаточно, операция отклоняется без изменения остатка и создания записи о движении.

Это позволяет предотвратить некорректное списание в проверенных сценариях параллельного доступа к PostgreSQL.

## Запуск через Docker Compose

### 1. Подготовка окружения

Скопируйте пример конфигурации:

```bash
cp .env.example .env
```

Для Windows:

```powershell
copy .env.example .env
```

Измените `DJANGO_SECRET_KEY` и `POSTGRES_PASSWORD` в `.env`.

### 2. Запуск приложения

```bash
docker compose up --build -d
```

Docker Compose запускает PostgreSQL и API. Перед стартом приложения автоматически выполняются миграции базы данных.

### 3. Создание администратора

```bash
docker compose exec api python manage.py createsuperuser
```

### 4. Доступ к приложению

После запуска доступны:

- Swagger UI: http://localhost:8002/api/docs/
- OpenAPI schema: http://localhost:8002/api/schema/
- Django Admin: http://localhost:8002/admin/
- DRF Login: http://localhost:8002/api-auth/login/

Для остановки контейнеров:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume.

## Локальный запуск без Docker

Создайте и активируйте виртуальное окружение Python 3.12.

Установите зависимости:

```bash
pip install -r requirements-dev.txt
```

Если переменная `POSTGRES_HOST` не задана, Django использует SQLite для локальной разработки.

Выполните миграции:

```bash
python manage.py migrate
```

Создайте администратора:

```bash
python manage.py createsuperuser
```

Запустите сервер:

```bash
python manage.py runserver
```

При локальном запуске стандартный адрес приложения — `http://127.0.0.1:8000/`.

Для проверки конкурентных операций рекомендуется PostgreSQL.

## REST API

Основные эндпоинты:

| Метод | Эндпоинт | Назначение |
|---|---|---|
| GET, POST | `/api/v1/products/` | Просмотр и создание товаров |
| GET, POST | `/api/v1/warehouses/` | Просмотр и создание складов |
| GET | `/api/v1/stocks/` | Просмотр складских остатков |
| GET, POST | `/api/v1/movements/` | История и создание складских операций |
| GET | `/api/schema/` | OpenAPI-схема |
| GET | `/api/docs/` | Swagger UI |

Просмотр данных доступен авторизованным пользователям. Изменение складских данных ограничено правами сотрудников.

### Пример поступления товара

`POST /api/v1/movements/`

```json
{
  "product": 1,
  "warehouse": 1,
  "kind": "receipt",
  "quantity": 10,
  "note": "Поставка товара"
}
```

### Пример списания товара

`POST /api/v1/movements/`

```json
{
  "product": 1,
  "warehouse": 1,
  "kind": "issue",
  "quantity": 4,
  "note": "Отгрузка"
}
```

Если доступного остатка недостаточно, API возвращает HTTP 400. Неуспешная операция не изменяет остаток и не создаёт запись в журнале.

## Тестирование

Проект содержит автоматизированные тесты API, прав доступа, валидации и складских операций.

В том числе проверяется конкурентное списание: два параллельных запроса пытаются списать больше товара, чем доступно на складе. Тест проверяет, что успешно выполняется только одна операция.

Запуск всех тестов через Docker:

```bash
docker compose exec api pytest -q
```

Запуск теста конкурентного списания:

```bash
docker compose exec api pytest inventory/tests/test_concurrency.py -v
```

Проверка качества кода:

```bash
docker compose exec api ruff check .
```

Проверка конфигурации Django:

```bash
docker compose exec api python manage.py check
```

## Continuous Integration

В проекте настроен workflow GitHub Actions (`.github/workflows/ci.yml`).

При отправке изменений в GitHub предусмотрены:

1. Запуск PostgreSQL 16.
2. Настройка Python 3.12.
3. Установка зависимостей.
4. Проверка конфигурации Django.
5. Проверка миграций.
6. Статический анализ Ruff.
7. Запуск тестов pytest.

Конфигурация CI подготовлена; её выполнение в GitHub Actions необходимо подтвердить после публикации репозитория.

## Ограничения и дальнейшее развитие

StockFlow реализует базовый контур складского учёта и не претендует на полнофункциональную WMS.

Возможные направления развития:

- Перемещения товаров между складами.
- Резервирование остатков под заказы.
- Расширение фильтрации и отчётности.
- Дополнительные нагрузочные и конкурентные тесты.
- Расширение ролевой модели доступа.
- Подготовка конфигурации для production-развёртывания.

## Безопасность

Секретные настройки хранятся в `.env` и исключены из Git.

Файл `.env.example` содержит шаблон переменных окружения.

Текущая конфигурация предназначена для локального запуска и демонстрации возможностей API. Публичное развёртывание требует отдельной production-конфигурации, HTTPS и дополнительной проверки безопасности.
